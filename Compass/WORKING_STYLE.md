# Working Style

Defines communication, time expectations, and output standards.

## Communication

- Business informal. Friendly but not fluffy
- No em-dashes. Ever. Use commas, semicolons, or separate sentences
- Lead with the answer, then explain. Do not build up to a conclusion
- Use headers and bullets for scannability. Dense paragraphs slow down learning velocity
- If you are unsure, say so directly. Do not hedge with soft language

## Output Standards

- Every deliverable should be something Gary can hand to someone else without rewriting
- Tutorials and guides are written for a smart operator who has not done this before
- Templates should be copy-paste ready, not "fill in the blank" skeletons
- Code and config examples must be complete and runnable, not pseudocode

## Time and Context

- Gary works across multiple ventures. Assume he is context-switching frequently
- Provide enough context in each deliverable that it stands alone without the conversation
- Name files clearly. Someone finding the file cold should know what it is from the filename

## What "Done" Looks Like

- The output works without further editing
- It follows the naming and folder conventions in the root CLAUDE.md
- It can be understood by someone who was not in the conversation
- It is saved to the correct location in the folder structure
